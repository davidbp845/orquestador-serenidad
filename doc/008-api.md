# API del chat web

Referencia de los endpoints HTTP que expone `adapters/in_/fastapi_app.py`.
Pensada para quien integra un cliente distinto al `frontend/` de este mismo
repo — el frontend ya incluido consume estos mismos endpoints, ver
`doc/004-arquitectura.md` para cómo encajan en el flujo completo de una
petición.

Base URL en desarrollo: `http://localhost:8000` (puerto fijo, definido en
`main.py::main()`).

## `POST /chat`

Respuesta completa, de una sola vez — la variante que usa también el bot de
Telegram internamente (aunque por un canal distinto, no HTTP).

**Request**

```json
{
  "usuario_id": "cliente-123",
  "mensaje": "¿tenéis hueco mañana para un masaje relajante?"
}
```

`usuario_id` identifica la conversación — dos mensajes con el mismo
`usuario_id` comparten `SesionConversacion` (historial incluido) vía el
puerto `RepositorioSesiones`; un `usuario_id` distinto empieza una
conversación nueva desde cero.

**Response** `200 OK`

```json
{
  "respuesta": "Sí, tenemos hueco mañana a las 10:00 y a las 16:30 con Ana. ¿Cuál prefieres?"
}
```

## `POST /chat/stream`

Mismo request body que `/chat`. La respuesta es
`text/event-stream` (Server-Sent Events) — el propio backend no usa
`EventSource` porque necesita mandar el mensaje en el body de un `POST`, algo
que `EventSource` no soporta; se consume a mano con `fetch` +
`ReadableStream` (ver `frontend/src/components/chat/useChatStream.ts` para
un cliente de referencia ya escrito).

Cabeceras de la respuesta: `Cache-Control: no-cache`,
`Connection: keep-alive`, `X-Accel-Buffering: no` (esta última evita que un
proxy tipo nginx acumule el stream en buffer antes de enviarlo, lo que
anularía el efecto de "streaming" en el cliente).

### Eventos

**`delta`** — cero o más, en orden, según el modelo va generando texto:

```
event: delta
data: {"texto": "Sí, tenemos"}
```

**`fuentes`** — como mucho uno por turno, justo antes de `done`. Notas del
vault usadas por el RAG en ese turno que están marcadas `publicar_web: true`
(ver `doc/005-conocimiento-del-negocio.md`) — las que el cliente puede
mostrar como enlace citable. Puede venir con lista vacía si el turno no usó
el RAG, o si usó solo notas no públicas.

```
event: fuentes
data: {"fuentes": [{"fuente": "horarios.md", "categoria": "horarios"}]}
```

**`done`** — exactamente uno, cierra el turno con el texto completo (mismo
contenido que iría acumulando los `delta` anteriores, ya concatenado):

```
event: done
data: {"respuesta": "Sí, tenemos hueco mañana a las 10:00..."}
```

**`error`** — en vez de `done`, si algo falla a mitad de la generación (p.
ej. el proveedor de LLM devuelve un error). La conexión no se corta en seco:
el fallo se convierte en un evento que el cliente puede mostrar como mensaje
de error legible.

```
event: error
data: {"mensaje": "descripción del error"}
```

### Ejemplo con `curl`

```bash
curl -N -X POST http://localhost:8000/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"usuario_id": "cliente-123", "mensaje": "¿qué precio tiene el masaje descontracturante?"}'
```

(`-N` desactiva el buffering de `curl`, necesario para ver los eventos
llegar incrementalmente en vez de todos de golpe al final.)

## `GET /health`

Sin autenticación, sin dependencias — no comprueba que el LLM, Chroma o
Postgres respondan, solo que el proceso FastAPI está vivo. Útil como
*liveness check* de un balanceador o supervisor de procesos.

```json
{"status": "ok"}
```

## CORS

Ver `doc/007-despliegue.md` — en desarrollo, los orígenes permitidos son los
puertos habituales de Vite/Astro (`:5173`, `:3000`, `:4321`); en producción,
`CORS_ORIGINS` los sustituye por el dominio real del frontend.

## Rate limiting

`POST /chat` y `POST /chat/stream` (no `GET /health`) están limitados por
`usuario_id` — no por IP — vía `adapters/in_/rate_limit.py` (#49): 20
peticiones cada 60 segundos por defecto, configurable con
`RATE_LIMIT_CHAT_MAX_PETICIONES`/`RATE_LIMIT_CHAT_VENTANA_SEGUNDOS`. Al
superarlo, la petición ni llega al orquestador:

**Response** `429 Too Many Requests`

```json
{"detail": "Demasiadas peticiones, espera un momento antes de volver a escribir."}
```

Sin `REDIS_URL` definida, el contador vive en memoria de cada proceso — con
varios workers/procesos el límite real efectivo es N veces el configurado.
Con `REDIS_URL` ya definida (ver `doc/003-modelo-datos.md`), el límite se
comparte automáticamente entre todos ellos vía ese mismo Redis, sin ninguna
variable de entorno adicional.

## Lo que esta API no tiene (todavía)

No hay autenticación en ninguno de los tres endpoints — `/chat`/`/chat/stream`
son deliberadamente públicos y abiertos, pensados para un chat de atención al
cliente sin login (el rate limiting de arriba frena el abuso evidente, no
sustituye a la autenticación). `doc/007-despliegue.md` documenta esto como
una decisión pendiente antes de un despliegue con tráfico público real, no
como un descuido de esta referencia.
